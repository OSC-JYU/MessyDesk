Design Principles

MessyDesk is built to support academic research, which has its own demands for data handling, reproducibility and method. Six principles guide how it is designed. They explain what MessyDesk does, and also what it deliberately does not do.

1. Chainable

Every output is a file that can be the input of the next tool.

2. Low barrier, no hand-holding

Easy to start, but you are expected to understand what you do.

3. You decide

No hidden automation. Every step is an explicit choice.

4. Transparent

Open tools, visible steps, nothing in a black box.

5. Humans and machines apart

Your work and machine output are never mixed.

6. Start light

Use the lightest method that works. Go heavier only if needed.

1. Chainable tools

MessyDesk tools are not endpoints that return a block of JSON and stop there. The result of every tool is a real file, shown as a node in your project graph, and that file can be given to any other tool that accepts its type.

  • An image can be cropped, then run through OCR, then translated, then searched.
  • A PDF can be split into pages, the pages turned into images, and the images processed further.
  • Each result is linked to its input, so a chain of steps stays a connected pipeline.

You build the chain one step at a time and can branch it anywhere to try a different approach on the same intermediate result.

2. Low technical barrier, no hand-holding

You do not need to install software, write code or run a command line. The visual interface lets you start working with your material right away.

The barrier to starting is low. The expectation to understand is not. MessyDesk does not turn research methods into a "one-click" wizard. It assumes you are willing to learn what a tool does, what its parameters mean and what its limits are. The tool descriptions are there to help, but the methodological choices remain yours.

3. No automation: explicit workflow, you decide

MessyDesk does not guess what you want and does not run processing in the background on its own. Nothing is OCR'd, translated or analysed unless you chose to run that tool, with those settings, on that file.

  • Every processing step starts from your explicit action.
  • Settings are visible and chosen by you, not hidden defaults.
  • The workflow is a record of your decisions, not of what the software decided for you.

💡 TIP: If you want to repeat or change a step, you can see exactly how it was made and run it again with different settings.

4. Transparency

In research you must be able to understand and defend how your material was processed. MessyDesk builds on trusted, open-source tools (such as Apache Solr, Poppler and Python libraries) and does not hide them behind a brand.

  • Dig into the exact algorithms that transform your data.
  • Cite specific, versioned tools and models in your publications.
  • Trace any file back to its source through the project graph, and see which tool and settings produced it.
  • Add notes on nodes to document your reasoning as you work.

A workflow you can see is a workflow a peer reviewer can follow and reproduce.

5. Strict separation of human labour and machine output

Data integrity depends on knowing who, or what, created a piece of information. MessyDesk keeps these two clearly apart:

Human labour

Your annotations, tags, drawn regions of interest (ROIs), notes and chosen pipeline settings. These are primary research data.

Machine output

OCR text, machine translations, detected objects or faces, summaries and other generated results. These are marked as algorithmic derivatives.

Machine errors and biases should never silently end up mixed into your hand-curated findings. Because the two stay separate, you can always tell what you made and what the machine suggested.

6. Green computing: start light, go heavier only if needed

Heavy models cost energy, money and time, and they are often not needed. MessyDesk encourages the lightest approach that does the job.

  1. Start with simple, fast tools, for example text extraction from a PDF or classic OCR.
  2. Look at the results and judge if they are good enough for your question.
  3. Only if they are not, move to a heavier method such as machine-learning models or generative AI.

💡 TIP: Try a heavy tool on a small sample first. If a light tool gives the same answer, you have saved a lot of computing.
